# Capabilities and release boundaries

## Transport and reuse

Gmail, Zoho and generic providers use IMAP/SMTP with operator-provisioned credentials (including app passwords where supported). OAuth, Gmail REST, Zoho REST and Microsoft Graph are not implemented. Provider account policies must permit IMAP/SMTP. No provider-specific labels/tags parity is claimed.

Configure each installation independently, outside the repository: explicit account IDs, endpoints, selectable inbox/sent folders, optional drafts folder, sender policy, attachment roots, database and keychain references. Do not copy another agent's credentials. The four-tool contract remains account-scoped.

## Query modes

- `folders`: selectable server paths and optional special-use role; never assume localized names.
- `list` / `search`: ascending UID pages in one folder. Filters from/to/cc/since/before/read/flagged/Message-ID and ASCII subject are evaluated server-side. A structured `subject` containing non-ASCII characters is matched locally against fetched envelope subjects after server-side filtering of the other criteria: NFC normalization and Unicode lowercase substring matching preserve accents and are not full Unicode case folding. This local subject search also supports `searchScope: allFolders`. Single-folder searches are limited to 2,000 candidates per scan. An all-folder local subject search examines an absolute 10,000-candidate budget across every selectable folder, independent of the requested page size and including nonmatches; an all-folder server-side search keeps the page-size-derived 100–2,000 candidate bound. Both are subject to the shared 512-window UID scan budget, the 32 MiB retained-metadata budget and a 60-second scan deadline, and fail closed instead of returning a partial page. The connection limits each IMAP response to 1 MiB and each literal or line to 512 KiB; exceeding a parser limit fails the request. Metadata is charged against a 32 MiB aggregate accounting budget across the whole scan using only the fields a summary retains (subject, Message-ID, date, From/To/Cc/Reply-To names and addresses, flags, size, In-Reply-To and bounded References): each retained value is charged its UTF-16 size plus a small fixed per-value and per-key overhead, while raw FETCH members the summary drops (`internalDate`, `bodyStructure`, `headers`, labels, `seq`, Sender, Bcc) are not charged. A single retained value above 65,536 code units, nesting beyond 8 levels or a cyclic shape fails closed as well. The 32 MiB figure covers an ordinary ~10,000-message mailbox with margin: a realistic message's retained projection costs about 1.4 KB, so 10,000 messages cost about 14 MiB and the budget holds about 22,700. Exceeding the candidate or metadata budget returns `QUERY_TOO_LARGE`. These are not peak-heap or process-memory ceilings: parsing, normalization, summaries and concurrent requests use additional memory. `hasAttachment` is unsupported and rejected.
- `searchScope: allFolders`: deduplicated Message-ID results sorted by date descending, folder then UID, with continuation cursor. Maximum 100 folders. The server-side candidate bound is 100–2,000 (dependent on requested page size); a local Unicode subject scan uses an absolute 10,000-candidate budget plus the 32 MiB retained-metadata budget and a 60-second deadline. Each following page repeats the whole scan from the first folder (the candidates of a local Unicode subject search are not cached across requests), so pagination costs one full bounded scan per page; the per-page bounds above are unchanged. Folder ordering and cursor comparison use UTF-16 code units, not locale collation, so distinct folder names never compare equal. Oversized requests return `QUERY_TOO_LARGE` (with `since`/`before` or single-folder guidance), not a supposedly complete partial result.
- List/search UID scans use windows of at most 1,024 UID values. Single-folder budget: 128 windows; global-search budget: 512 windows. Thread header lookups use larger but still bounded windows of at most 65,536 UIDs, with a 512-window total budget and existing candidate/result caps. Sparse high-UID mailboxes can exceed budgets even when few messages match; this is bounded IMAP search, not universal webmail conversation parity.
- Cursors are opaque encoded values, not credentials or authorization grants; pass `nextCursor` unchanged with the same account, folder and search. Global cursors bind the account, query and structured filters and reject changed folder generations/UIDNEXT. Single-folder Unicode subject cursors bind the query, UIDVALIDITY and observed UIDNEXT; a changed UIDNEXT observed when selecting a later page is rejected as `REFERENCE_STALE`. The in-scan value is cached and does not guarantee detection of new arrivals during a scan.
- **Neither cursor is a transactional snapshot.** UIDNEXT bounds the UID range but does not snapshot flags, message existence or other mailbox changes. External flag changes can make messages enter or leave `isRead`/`isFlagged` results, including behind the cursor; deletion or expunge can remove candidates or results without changing UIDNEXT. Changes during or between pages can therefore produce omissions or a mixed-time view without a stale-cursor error. Restart after a stale cursor and when consistency matters, but even a restart does not guarantee a snapshot while the mailbox is changing; use a quiescent mailbox or an independent snapshot mechanism for a consistent inventory.
- `read`: verified bounded full MIME read; public response contains bodies and attachment metadata, not raw MIME or attachment content. Full MIME is fetched in contiguous chunks of at most 64 KiB, with a one-byte probe at the accumulated offset requiring an explicit zero-length `BODY[]` literal to confirm EOF. Missing source data is not EOF; a short interior chunk followed by more bytes fails closed. Every fetch must retain the requested UID and mailbox generation. `RFC822.SIZE` must be valid nonnegative integer metadata but is only a hint, not proof of completeness or the read-limit decision: overstated and understated hints are tolerated when the actual bytes and EOF verify. A byte beyond the configured read bound returns `MESSAGE_TOO_LARGE`; exactly the bound is accepted only after explicit EOF. Successful full reads report the verified raw MIME byte count as `size`; list/search metadata may still carry the provider's size hint.
- `attachments`: metadata-only listings expose provider BODYSTRUCTURE octets as optional `encodedSize` (raw transfer-encoded MIME part length); they do not claim this is decoded file size. Explicit zero-based `attachmentIndex` downloads return `size` as decoded file octets, base64 bytes, and SHA-256. Base64 expands response size; receiving agents must provision an adequate tool-output budget. SHA-256 identifies returned bytes, not provider authenticity.
- `thread`: bounded relationships inferred from the anchor's Message-ID, In-Reply-To and References across selectable folders or current folder. Header criteria are searched individually for Zoho compatibility, in UID windows up to 65,536 values to reduce round trips while retaining a 512-window total budget and candidate/result caps. This is not recursive provider-native conversation discovery. A successful result means the bounded anchor-derived lookup completed, not that every possible descendant or malformed-header message exists in the result. Optional bodies: at most 20 messages, aggregate bound and per-message verified read bound. The aggregate budget sums each completed read's verified raw MIME byte count, not the summaries' `RFC822.SIZE` hints; crossing it returns `THREAD_TOO_LARGE`, not a partial successful thread. This counts full MIME, including encoded attachments, rather than only displayed body text. No embedded attachment bytes. These are verified raw-byte budgets, not strict heap-memory ceilings: one additional per-message-bounded read may complete before aggregate overflow is detected, and MIME parsing, chunk concatenation and attachment copies add transient allocations. EOF verification assumes a conforming server; it does not authenticate the bytes, detect dishonest EOF claims or guarantee a snapshot across multiple fetches.

## Outgoing mail and drafts

Send/reply/forward use durable prepared MIME, stable Message-ID, To/CC/BCC, attachment manifests, account policy and idempotency. BCC is not exposed in received public projections. SMTP acknowledgment and Sent verification are separate outcomes. Unknown delivery and acknowledged-but-unverified sends cannot be blindly retried. Sent policy is explicit; Gmail/Zoho default to provider-managed copies.

Draft intent may omit recipients. `saveDraft` appends persisted MIME once with Draft flag to configured/discovered Drafts; ambiguous writes remain verification-required. Saved drafts can be read and moved to Trash via their mailbox reference. Editing/sending an existing provider draft in place and automated ambiguous-draft reconciliation are not implemented. Prepare a new message deliberately rather than claiming provider draft lifecycle parity.

## Mailbox actions

Mark read/unread, add/remove standard Flagged/Answered flags, move/copy, Trash and restore. Archive uses move/copy to a discovered operator-selected archive folder; no dedicated archive action. Trash discovery requires a selectable special-use Trash role. Restore targets configured Inbox, not the former folder. No EXPUNGE or permanent delete API is exposed. MOVE/COPY require provider UIDPLUS-style destination mapping; a successful server write with an unconfirmable response is not safe to blindly repeat.

## Verification and deployment

Local tests and synthetic IMAP fixtures demonstrate application/protocol behavior only. They do not demonstrate Gmail/Zoho live compatibility. Run typecheck, build, full tests, audit, scoped secret/diff checks and compiled stdio protocol tests before release. Then perform separately authorized read-only provider validation. Never send test email without an approved controlled recipient.

Code merged on GitHub does not update an already running MCP process. Each agent must install the release, compile, provision its own external config/credentials, reload its MCP and verify actual tool discovery plus provider behavior. Do not claim deployment from repository presence alone.
